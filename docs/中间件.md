# 中间件(AgentMiddleware)体系

本文档说明 DeerFlow 的中间件机制——基于 LangChain 1.0 的 `AgentMiddleware`。这是 [工具(Tools)体系](./tools.md) 的姊妹篇:`tools.md` 里提到的中间件(`TitleMiddleware`、`ClarificationMiddleware`、以及尚未实现的 `ViewImageMiddleware`)在本文逐一审视,并核对每个的实现是否正确。

如果你只想记住一句话:**中间件就是「Agent 主循环上、若干固定位置预留的可插拔工位」,你把自定义函数挂到对应工位(hook)上,框架会在那个时机自动调用它**。

---

## 设计理念:中间件 = 流水线上的可插拔工位

`create_agent` 给你的 Agent 本质是一个 LangGraph 图,有一条固定的「主循环」。但你常常想在循环的某些环节「插一脚」,例如:

- 整个会话开始前,初始化一下状态;
- 每次调模型前,把当前用户身份塞进 system prompt;
- 每次调模型后,顺手给会话生成一个标题;
- 某个工具被调用前,检查它是否安全,或直接拦截它;
- 整个会话结束后,做收尾统计。

框架把这些「插一脚」的位置提前留好了,叫 **Hook(钩子)**。你写的 `AgentMiddleware`(来自 `langchain.agents.middleware`),本质上就是**一组挂在这些固定位置上的自定义函数**。

> **类比**:把 Agent 图想成一条餐厅厨房流水线(点单 → 厨师思考 → 取食材 → 出菜)。中间件不是新增加一道菜,而是流水线旁一排「可插拔的质检工位」——你在「接单前」「出菜后」「取食材前」放上一个工位,挂上自己的检查函数,流水线经过时就自动执行。不需要时,不挂这个工位即可,主线一字不改。

---

## 前置认知:Agent 的主循环

理解 Hook 的前提,是先知道 Agent 内部在循环什么。Agent 图的核心是**两个节点在循环**:

- **model 节点**:调用大模型,让它「思考」;
- **tools 节点**:执行模型决定调用的工具。

Hook 不是随便触发的,它们就挂在这条循环的固定位置:

```
开始
  │
before_agent        ← 整个会话开始前,只跑一次
  │
  ▼
┌─── 循环(每一轮)─────────────────────────────┐
│                                                │
│   before_model         ← 每次调模型前           │
│        │                                       │
│        ▼                                       │
│   wrap_model_call ──► 【真正调用模型】          │
│        │                                       │
│        ▼                                       │
│   after_model          ← 每次调模型后           │
│        │                                       │
│      模型这次想调工具吗?                        │
│      ├─ 想 → wrap_tool_call ─►【执行工具】─┐    │
│      │                                      └─► 回到 before_model,进入下一轮
│      └─ 不想 → 跳出循环                        │
└────────────────────────────────────────────────┘
  │
  ▼
after_agent         ← 整个会话结束后,只跑一次
  │
结束
```

## Hook 全家福:8 个挂钩点

`AgentMiddleware` 基类定义了 8 个方法(成对的 `xxx` / `axxx` 分别是同步 / 异步版,功能相同)。按能力从弱到强分三类。

### 生命周期 Hook(最简单,会话级)

| Hook | 何时触发 | 典型用途 |
| --- | --- | --- |
| `before_agent` / `abefore_agent` | 整个会话**开始前**,一次 | 初始化状态、记录会话开始 |
| `after_agent` / `aafter_agent` | 整个会话**结束后**,一次 | 收尾统计、清理资源 |

它们只能「看一眼状态、改一点状态」,无法插手循环内部。

### 模型前后 Hook(每轮都跑)

| Hook | 何时触发 | 典型用途 |
| --- | --- | --- |
| `before_model` / `abefore_model` | **每轮**调模型前 | 注入额外上下文、动态改 prompt、推「正在思考」状态 |
| `after_model` / `aafter_model` | **每轮**调模型后 | 给本轮输出打标签、**自动生成标题**、内容审核 |

> DeerFlow 的 `TitleMiddleware`(见 `agents/middlewares/title_middleware.py`)就是典型的 `after_model`:模型回完第一句话后,顺手给会话生成标题,写进 `ThreadState.title`。

### 包裹式 Hook(最强大,洋葱模型)

| Hook | 包裹的对象 | 能干什么 |
| --- | --- | --- |
| `wrap_model_call` / `awrap_model_call` | 整个**模型调用** | 重试、换备用模型、缓存、短路、改写回复 |
| `wrap_tool_call` / `awrap_tool_call` | 整个**工具调用** | 拦截工具、改参数、重试、记录耗时、短路 |

它俩和前两类有本质区别——看签名就懂,这一节单独讲。

## 难点:包裹式 Hook 的 handler 模式

普通 Hook 是「被动观察」,包裹式 Hook 是「主动控制」,区别在参数里多了一个 `handler`:

```python
# 普通 hook:被动观察,返回状态更新即可
def after_model(self, state, runtime):
    return {"title": "天气闲聊"}   # 返回 dict → 更新 state

# 包裹式 hook:主动控制,手里攥着「是否执行」的开关
def wrap_tool_call(self, request, handler):   # ← 多了 handler
    result = handler(request)   # 调它 = 放行,执行工具
    return result
```

`handler` 就是**「真正去执行模型 / 工具」**的那把钥匙。围绕它有三种玩法:

1. **正常放行**:`return handler(request)` —— 工具 / 模型照常执行;
2. **短路 / 拦截**:**不调用** `handler`,自己返回一个结果 —— 工具 / 模型根本不执行;
3. **重试**:在 `for` 循环里多次调用 `handler` —— 失败就重来。

> 这正是 `ClarificationMiddleware` 的玩法(玩法 2,短路)。`tools.md` 里讲过:`ask_clarification` 是个「占位工具」,自己不做真正的逻辑。模型想用它向用户追问时,中间件用 `wrap_tool_call` 把这次调用**拦下来不让它真执行**,而是直接打断 Agent、把澄清问题抛回给用户。伪代码:
>
> ```python
> def wrap_tool_call(self, request, handler):
>     if request.tool_call["name"] == "ask_clarification":
>         question = request.tool_call["args"]["question"]
>         # 不调 handler → 工具不执行;用 Command 跳到终点,把问题返回给用户
>         return Command(goto="end", update={"messages": [...]})
>     return handler(request)   # 其他工具正常放行
> ```

`wrap_model_call` 同理,常用玩法是「重试」和「换备用模型」:

```python
def wrap_model_call(self, request, handler):
    for attempt in range(3):
        try:
            return handler(request)        # 调模型
        except Exception:
            if attempt == 2:
                raise                       # 最后一次仍失败,抛出
    # 或:失败后换成备用模型再试一次
    # return handler(request.override(model=fallback_model))
```

## 两种写法

### 方式 A:继承 `AgentMiddleware` 类(适合复杂逻辑)

一个类里可以同时实现多个 Hook,它们属于同一个「中间件单元」,能共享状态:

```python
from langchain.agents.middleware import AgentMiddleware

class TitleMiddleware(AgentMiddleware):

    def after_model(self, state, runtime):
        if state.get("title"):
            return None
        return {"title": str(state["messages"][0].content)[:20] + "…"}
```

### 方式 B:用装饰器(适合简单逻辑,一行起步)

装饰器会在背后**自动**把函数包成一个 `AgentMiddleware` 实例。可用装饰器:`@before_agent` / `@after_agent` / `@before_model` / `@after_model` / `@wrap_model_call` / `@wrap_tool_call` / `@dynamic_prompt`。

```python
from langchain.agents.middleware import before_model

@before_model
def log_round(state, runtime):
    print(f"即将调用模型,当前消息数: {len(state['messages'])}")
```

> **类比**:方式 A 是「自己组一支乐队」(一个类可挂多个 hook、可带配置);方式 B 是「点一首单曲」(一个函数 = 一个只挂单个 hook 的中间件)。逻辑简单用 B,需要多个 hook 协同或有配置项时用 A。

## Hook 手里的三样法宝

不管哪种写法,Hook 能「干大事」靠的是三样东西。

### 法宝一:`state` —— 共享状态(读写)

每个 Hook 都能拿到 `state`,它就是 DeerFlow 的 `ThreadState`(见 `agents/thread_state.py`)。Hook 通过**返回 dict** 来更新它:

```python
def after_model(self, state, runtime):
    return {"title": "关于天气的闲聊"}   # → 写入 ThreadState.title
```

`artifacts`、`todos`、`viewed_images` 这些字段都是设计给中间件(或工具)去写的,且配了自定义 reducer(`artifacts` 去重、`todos` 整个替换、`viewed_images` 浅合并),写入语义见 `tools.md` 的「`ThreadState` 字段一览」。

### 法宝二:`jump_to` —— 控制流程走向

`before_model` / `after_model` 可以返回 `{"jump_to": "tools" | "model" | "end"}` 来**强行改变流程**:跳去执行工具 / 跳回模型 / 直接结束。

```python
from langchain.agents.middleware import hook_config

class GuardMiddleware(AgentMiddleware):
    @hook_config(can_jump_to=["end"])   # ⚠️ 必须声明,图才知道这条岔路存在
    def before_model(self, state, runtime):
        if detect_sensitive(state):
            return {"jump_to": "end"}   # 拦截,不调模型了
        return None
```

> **关键**:用 `jump_to` 必须配合 `can_jump_to` 声明(类写法用 `@hook_config` 装饰器,装饰器写法用 `@before_model(can_jump_to=[...])`)。否则 LangGraph 不知道要给图加这条边,跳转不生效。

### 法宝三:`runtime` —— 运行时上下文(含流式推流)

`runtime` 里最常用的是 `runtime.stream_writer`,能在流式输出时给前端**推自定义事件**:

```python
@before_model
async def notify_thinking(state, runtime):
    runtime.stream_writer({"type": "status", "message": "正在思考..."})
```

前端用 `stream_mode="custom"` 即可收到这些事件,用来渲染「正在思考…」「正在调用工具…」这类 UI 反馈。

## 洋葱模型:多个中间件怎么叠加

`create_agent(middleware=[A, B, C])` 时,**列表里第一个是最外层**。包裹式 Hook 像洋葱一样层层套住真正的执行:

```
请求 →  A  →  B  →  C  → 【真正调用模型 / 工具】 →  C  →  B  →  A  → 响应
       最外层              (handler)                        最外层
```

- 想「最外层先看到请求」的中间件(如全局日志、缓存)**放列表前面**;
- 普通 before / after Hook 也按列表顺序依次执行;
- 对同一份状态的修改:带 reducer 的字段(如 `messages`、`artifacts`)**会合并**,普通字段则**后者覆盖前者(最外层赢)**。

### 0. `LLMErrorHandlingMiddleware` —— 模型 API 异常处理(✅ 已修复)

- **Hook**:`wrap_model_call`(最外层)
- **作用**:try/except 包住模型调用,按错误特征分类(auth / retryable / fatal)。
- **正确性**:✅ **已修复**。原实现三分支全部 `raise`,只记日志不降级(名实不符);现已改为:
  - 可重试错误(限流 429 / 超时 / 过载)→ 指数退避重试(`max_retries` 次);
  - 认证 / 配置错误、或重试耗尽 → 返回兜底 `AIMessage`(`wrap_model_call` 支持直接返回 `AIMessage`,会自动转 `ModelResponse`),Agent 优雅降级而非崩溃。

### 1. `DynamicContextMiddleware` —— 动态上下文注入(✅ 已修复,记忆留空)

- **Hook**:`wrap_model_call`
- **作用**:每轮模型调用前,把「今天日期」等动态信息以 `<system-reminder>` 包裹的 `SystemMessage` 注入到对话消息最前面。
- **正确性**:✅ **已修复**(记忆注入仍留空,属「阶段4」范畴)。原实现三点瑕疵,已改:
  - 改用 `wrap_model_call`(而非 `before_agent`)→ 每轮注入;且注入的提醒**不写回 state**,下一轮 `request.messages` 不含它 → **不累积**;
  - 改用 `SystemMessage`(而非普通 `HumanMessage`)→ 不与用户消息混淆;
  - 仅 `request.override(messages=...)`,不改 `system_message` → 保留缓存友好性。

### 2. `ToolErrorHandlingMiddleware` —— 工具异常兜底(✅ 范例)

- **Hook**:`wrap_tool_call`
- **作用**:try/except 包住工具执行,把异常转成 `status="error"` 的 `ToolMessage` 返回给模型,单工具失败不拖垮整个 Agent。
- **正确性**:✅ **写得最规范的一个**。关键正确点:单独 `except GraphBubbleUp: raise` ——LangGraph 的控制流信号(interrupt / pause / resume / `Command(goto=END)`)靠 `GraphBubbleUp` 异常传递,**绝不能被 `except Exception` 吞掉**,否则 `ClarificationMiddleware` 的中断会在此失效。错误消息正确取 `tool_name` / `tool_call_id`、截断 500 字符。

### 3. `TitleMiddleware` —— 自动生成标题(✅ 已修复)

- **Hook**:`after_model`
- **作用**:首轮 user→ai 完整对话后,从 AI 回复生成标题写进 `state.title`,只生成一次(`_should_generate_title` 已有 title 则跳过,逻辑正确)。
- **正确性**:✅ **已修复**。两个原问题:
  - **中文标题超长 bug(核心)**:原 `content.split()[:max_words]` 按空白切分,中文无空格 → 标题变整句回复。已改为按**字符**截断 `text[:max_words] + "…"`,中文按字数计数。测试印证:标题已从整句变为 `你好小明！👋 很高兴…`。
  - **LLM 生成未实现**:原 `TITLE_PROMPT`(让 LLM 生成标题)是死代码、未被调用,已删除。当前为字符截取版(够用);未来可在此接入 LLM 生成更精炼标题。

### 4. `MemoryMiddleware` —— 对话入队(🚧 半成品)

- **Hook**:`after_agent`
- **作用**:`after_agent` 收集本轮 user/ai 对话对,塞进实例队列 `self._update_queue`,「供后台异步提取记忆」。
- **正确性**:🚧 **半成品**(注释自述「阶段4」)。只入队,**无人消费**:没有后台线程、没有 LLM 提取记忆、没写进 state、没落库(config 里 `database: sqlite`、`memory.max_facts` 都是为它预留的)。注入端 `DynamicContextMiddleware` 也留空。收集逻辑本身能跑,但产出无人使用——这就是「记忆中间件为什么没起作用」的根因:它对 Agent 行为的影响为零。

### 5. `LoopDetectionMiddleware` —— 重复工具调用检测(✅ 范例)

- **Hook**:`after_model` + `wrap_model_call`
- **作用**:哈希模型每轮的工具调用列表(name+args 规范化);滑动窗口内同一模式重复 ≥`warn_threshold` 在下一轮注入警告提示模型;≥`hard_limit` 强制清空 `tool_calls` 转文本回复。
- **正确性**:✅ **质量高**,两个关键正确点:
  - 硬限制时用 `last_msg.model_copy(update={"tool_calls": [], ...})` 而非原地赋值——`AIMessage` 是 Pydantic v2 frozen model,原地改抛 `ValidationError`。`model_copy` 保留原 `id`,配合 `add_messages` 的「同 id 替换」语义,能正确**替换**那条 AIMessage 而非追加。
  - 警告注入用 `request.override(messages=request.messages + [warning_msg])`,不可变风格,正确。
- **小瑕疵**:`_call_history` / `_pending_warnings` 是实例 dict、非线程安全(注释承认),教学版可接受。

### 6. `ClarificationMiddleware` —— 澄清拦截(⚠️ HITL 未完整)

- **Hook**:`wrap_tool_call`(链最后)
- **作用**:拦截 `ask_clarification` 工具,用 `Command(goto="__end__")` 结束本轮执行,把澄清问题以 `ToolMessage` 返回给用户。
- **正确性**:⚠️ 核心能工作;`goto` 已由硬编码 `"__end__"` 改为 import 的 `END` 常量。仍存(属功能未完成,非 bug):「等待用户回复后继续」未实现——`goto=END` 只**结束当前执行**,不等于 human-in-the-loop 的「挂起等回复」。真正 HITL 需 `interrupt()` + `Command(resume=...)`(「阶段3」后续工作),当前是「停止 + 返回问题」,对最小目的够用。
- ✅ 必须排最后(装配顺序保证),与 `ToolErrorHandlingMiddleware` 的 `GraphBubbleUp` 放行配合,控制流信号不会被吞。

## 动手骨架:写第一个中间件

一个完整、贴合 DeerFlow 的 `TitleMiddleware`,可直接复制:

```python
from langchain.agents.middleware import AgentMiddleware

class TitleMiddleware(AgentMiddleware):
    """第一轮对话后,自动给会话生成标题。"""

    def after_model(self, state, runtime):
        # 已有标题就跳过(避免每轮都覆盖)
        if state.get("title"):
            return None
        # 取用户的第一句话当素材(真实场景可在此再调一次小模型生成标题)
        first_msg = state["messages"][0]
        title = str(first_msg.content)[:20] + "…"
        return {"title": title}   # → 写入 ThreadState.title
```

## 避坑清单

1. **同步 / 异步要配对**:用 `invoke()` 就实现 `before_model`(同步);用 `ainvoke()` / `astream()` 就实现 `abefore_model`(异步)。`wrap_*` 系列若只写了同步版却在异步上下文里跑,会抛 `NotImplementedError`。
2. **`jump_to` 必须声明 `can_jump_to`**,否则跳转静默失效。
3. **包裹式 Hook 别忘了 `return handler(request)`**,否则所有工具 / 模型调用都会被你拦死。
4. **改请求用不可变风格**:`request.override(system_message=...)` 返回新对象,不要直接赋值改原对象(会有 deprecation 警告)。
5. **列表顺序 = 洋葱层级**,第一个最外层;普通 before / after Hook 也按此顺序执行。

---

## 如何选择 Hook

按需求对照下表选型:

| 需求 | 选哪个 Hook | 说明 |
| --- | --- | --- |
| 会话开始 / 结束各做一次事 | `before_agent` / `after_agent` | 只触发一次 |
| 每轮调模型前后做点事 | `before_model` / `after_model` | 每轮触发,返回 dict 改 state |
| 根据条件提前结束或改走 tools / model | `before_model` / `after_model` + `can_jump_to` + `jump_to` | 控制流 |
| 动态生成 system prompt | `wrap_model_call`(或 `@dynamic_prompt` 装饰器) | 改 `request` 后再 `handler` |
| 模型调用要重试 / 换备用模型 / 缓存 | `wrap_model_call` | 玩转 `handler` |
| 拦截某个工具不让它真执行 | `wrap_tool_call`(短路) | 不调 `handler` |
| 给工具加重试 / 改参数 / 记耗时 | `wrap_tool_call` | 放行但加料 |
| 给前端推「正在思考…」等状态 | `before_model` 等 + `runtime.stream_writer` | 搭配 `stream_mode="custom"` |

> 一句话总结:`before_*` / `after_*` 是「在门口签到」(被动、改 state、控流向);`wrap_*` 是「当门卫」(主动、攥着 `handler` 开关、能重试能短路)。需要「拦下不让执行」或「失败重试」时,才轮到 `wrap_*`。
